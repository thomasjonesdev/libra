# 5.9 App Module Layout

## In this vault

- Parent: [[05-state-and-actions]]
- Siblings this leans on: [[05.2-macro-expansion|§5.2]] (fixed names), [[05.8-app-assembly|§5.8]] (`app!`), [[06.3-grammar-restrictions|§6.3]] (`#[project]` / derived fields)

## In code

- `examples/notes/src/` — the reference `model.rs` / `state.rs` / `actions.rs` / `lib.rs` split

---

An app starts as one `lib.rs` and should stay that way while it fits —
counter, fetcher, todos, and dashboard are all single-file and correct.
When the file stops fitting in one read (≈200+ lines, or when domain
logic starts dominating the action methods), it splits into **exactly
four files**. This is the one documented shape; don't invent per-app
variants:

| File | Owns | Knows about |
|---|---|---|
| `model.rs` | Pure domain: data types, `Display`/row types for `<for>`, store formats + migration, derivation helpers (title/snippet/label functions) | serde, `LibraReflect` for row types. **No `Effect`, no `Action`, no view** — plain Rust, unit-testable without a Harness |
| `state.rs` | The one `#[libra::state]` struct + inherent helpers (`init`, hydration, shared machinery like save scheduling) | `model`, `Action` (for effect ctors), `Effect` |
| `actions.rs` | The one `#[libra::actions]` block: every handler, every continuation, the `#[project]` hook | `model`, `state` |
| `lib.rs` | Wiring only: crate doc, `mod` declarations, **re-exports**, `libra::app!` | everything, thinly |

The reference implementation is `examples/notes` (§5.9 adopted at
~640 lines; the split left a 46-line `lib.rs`). The layering mirrors
[[06.3-grammar-restrictions|§6.3]] at
file granularity: computations live in `model.rs`, the State fields
they fill live in `state.rs`, and the `#[project]` hook in `actions.rs`
connects them.

## The constraints that force this shape (not style preferences)

1. **One `#[libra::actions]` block per module, fixed names.** The macro
   generates `pub enum Action` and `pub fn reduce` *in the module that
   invokes it* (§5.2). So there is exactly one `actions.rs`, and it is
   the only place those names are born. Wanting a second block is not a
   file-layout problem — it's [[05.7-state-slices|§5.7]]
   slices, which are not built yet.
2. **`app!` stays in `lib.rs`.** Its `view:` path feeds `include_str!`,
   which resolves relative to the *invoking file*; the generated
   `pub const VIEW` and `pub fn run()` also belong at the crate root
   where `main.rs` and the tests expect them (§5.8).
3. **The re-export contract.** `lib.rs` restores the flat, single-file
   surface:

   ```rust
   mod actions;
   mod model;
   mod state;

   pub use actions::{reduce, Action};
   pub use model::{/* domain types + constants tests assert on */};
   pub use state::Notes;

   libra::app! { state: Notes, view: "../views/notes.lx", /* … */ }
   ```

   `app!` resolves `Action`/`reduce`/the state type through these
   re-exports; the test files keep importing `myapp::{Action, reduce,
   Notes, VIEW, …}` — **a split must never change a test import**. That
   is the acceptance check for the refactor: all four test kinds green
   with zero test-file edits, snapshots byte-identical.

4. **Circularity is fine, hiding is not.** `state.rs` references
   `Action` (effect ctors in `init`/helpers) while `actions.rs`
   references the state type — ordinary sibling-module imports within
   one crate. Keep the modules themselves private (`mod state;`, not
   `pub mod`) and mark items `pub`; only the `lib.rs` re-export list is
   public API. State helpers that only actions call are `pub(crate)`
   (`hydrate`, `schedule_save`), not `pub` — the struct itself is
   re-exported, so a `pub` method would leak into the crate's surface.

## What not to do

- **Don't split `actions.rs` further** (one file per action group).
  One block per module is a macro invariant; grouping happens with
  comment sections inside the block, and real decomposition is §5.7's
  job when it lands.
- **Don't move `app!` or add nesting** (`src/domain/…`). Four flat
  files is the shape; an app that outgrows it is outgrowing the
  single-State design, which again points at §5.7, not at more folders.
- **Don't reach into `crate::model` from tests.** If a test needs a
  type or constant, add it to the `lib.rs` re-export list — the module
  tree is an implementation detail.
