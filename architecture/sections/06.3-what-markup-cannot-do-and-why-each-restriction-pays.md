# 6.3 What markup CANNOT do — and why each restriction pays

## In this vault

- Parent: [[06-the-view-layer-and-markup]]

---

| Restriction | What it buys |
|---|---|
| No arbitrary expressions | Static validation; the interpreter and codegen stay simple and provably equivalent |
| No state mutation | Views are pure projections; hot reload can never corrupt state |
| No inline closures | Every handler is a named `Action` — greppable, loggable, replayable |
| No side effects | Rebuilding a view is always safe, any number of times |
| No arbitrary computation | Anything complex belongs in the State as a derived field — where it is testable |

The rule of thumb, borrowed intact from Elm: **if you want to compute it, put it on the State.** `visible_items` is a state field maintained by actions (or a memoized derivation), not a filter expression in markup.

## Display projections are maintained by the framework, not by discipline

The restriction above creates derived fields (`active`, `done`, `summary` in the todos example) — and derived fields create a staleness hazard if every action must *remember* to rebuild them. That treadmill is not part of the design; it was an implementation gap, closed 2026-07:

- Mark one `fn project(&mut self)` in the `#[libra::actions]` block with **`#[project]`**. It is not an action (never enters the `Action` enum, never nameable from markup); it is the projection step.
- The generated `reduce` calls it **after every action** — handlers and effect-result continuations alike. Since the view tree rebuilds after every dispatch and only then, "recomputed after every reduce" is observationally identical to React's "derived during render." Actions just mutate the source-of-truth fields; projections can never be stale.
- The default `init` (when `libra::app!` has no `init:` field) is the projected default: `Default::default()` run through `#[project]` — correct derived fields from frame zero with zero user code. A custom `init:` owns its own initial projection (call the project fn once).
- Purity is unchanged (§5.3): `#[project]` is `state → state`, deterministic, replayable — it is *part of* the reduce step, not a new phase.

**Considered and rejected — render-time computed getters** (`fn active(&self) -> Vec<String>` bound directly by name, the literal React shape): the codegen engine compiles bindings to direct field access (`state.active.iter()` — [[06.4-one-grammar-two-engines|§6.4]], [[06.5-compile-time-validation-the-part-react-cannot-give-you|§6.5]]), and a binding name can't syntactically distinguish field from method. Routing all bindings through generated accessors would be invasive across the dual-engine boundary for zero observable difference. If `{item.field}` sub-bindings (§26) ever force accessor indirection anyway, revisit then.

The same rule settles the tempting middle ground of letting `.lx` hook into "small reusable pure functions": rejected. That reusable-pure-function layer already exists — it is the actions impl ([[05-state-and-actions|§5]]) — and it lives in Rust, where the type system checks it, unit tests exercise it, and the action log records it. A function hook in markup would reopen everything the closed grammar buys: static validation, interp≡codegen equivalence, and hot reload that cannot corrupt state.
