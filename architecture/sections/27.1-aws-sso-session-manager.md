## The job

An AWS IAM Identity Center (SSO) token in this environment lasts about eight
hours. Keeping a working session today means remembering that, noticing when it
lapsed — usually by way of a command failing — and re-running a script from a
terminal with the right flags. `refresh_aws_sso.sh` already removed the worst
part (it stopped re-asking for the SSO URL, region, and profile on every
refresh) but it left the two things a script cannot fix: you have to remember to
run it, and you have to be in a terminal to do so.

The app's promise is narrow and complete: **first run walks you through setup
once; after that there is one button, and the session stays alive on its own.**

Everything the script does, the app does — the difference is that the script's
control flow becomes State, its `aws` invocations become
[[12.6-the-process-effect|§12.6]] effects, and its saved
`~/.config/aeos/aws-sso.env` becomes `Effect::Kv*` ([[13.1-kv-store|§13.1]]).

## Three modes

The app is always in exactly one of these, chosen by State, rendered by
`<if>` — not by navigation. There is no route to get "lost" in.

| Mode | When | What it shows |
|---|---|---|
| **Preflight** | `aws` missing or not v2 | What is missing, and how to fix it. Nothing else is reachable. |
| **Onboarding** | no saved config, or the user asked to redo it | One form of org defaults → writes `~/.aws/config` → first login |
| **Steady state** | configured | Status, one **Authenticate** button, the current config, a way back to onboarding |

Preflight outranks the others because every other mode is a lie without a CLI
to run. It checks two things:

- **`aws` v2 — required.** `aws --version` prints `aws-cli/2.x.y …`; the app
  parses the major version and refuses to proceed on v1 or on a missing binary.
  Remediation copy names Company Portal first (where this environment gets it)
  and the AWS installer docs second.
- **`claude` — advisory.** Checked with `claude --version` and reported, never
  blocking. It is part of the wider workstation setup, not of AWS auth, and an
  AWS session manager that refuses to work because an unrelated CLI is absent
  would be an annoyance dressed up as rigor.

## Configuration: two stores, one owner each

Nothing is duplicated between them, because duplicated config is config that
disagrees.

**`~/.aws/config`** is AWS's, written only through `aws configure set` — the app
never edits the file directly. It receives the `sso-session` block and the
profile, exactly as `bootstrap_sso_config` writes them today:

```
[sso-session <session>]        sso_start_url, sso_region, sso_registration_scopes
[profile <profile>]            sso_session, sso_account_id, sso_role_name, region
```

**The app's KV store** holds what the app itself needs to remember, and nothing
else: the chosen session name, profile name, the org defaults last used, and
whether unattended refresh is enabled. It holds **no credential, no token, and
no identity**. The seed defaults match the script (session `aeos-govcloud`,
region `us-gov-west-1`, scopes `sso:account:access`, profile
`<role>-<account>`), and every one of them is editable in onboarding.

## The command surface

The app may run these and nothing else. This list *is* the
[[12.6-the-process-effect|§12.6]] allowlist for this application, and it is
deliberately short enough to read:

| Purpose | argv |
|---|---|
| Preflight | `aws --version` · `claude --version` |
| Write config | `aws configure set <dotted.key> <value>` |
| Read config | `aws configure get <dotted.key>` · `aws configure list-profiles` |
| Log in | `aws sso login --profile <p>` |
| Verify | `aws sts get-caller-identity --profile <p>` |
| Sign out | `aws sso logout` |

Notably absent: **`aws configure export-credentials`**. It would give an exact
token expiry for a precise countdown, and it prints the secret access key and
session token to stdout to do it. That trade is refused — see *Security* below.

### Deviation: `aws configure set`, not `aws configure sso`

The setup instructions for this environment say to run `aws configure sso`. The
app does not, and this is a deliberate departure worth stating plainly.

`aws configure sso` is an **interactive TTY prompt flow**. Driving it from a GUI
would require a pseudo-terminal and streamed output, neither of which
[[12.6-the-process-effect|§12.6]] provides (nor should, for this). The sequence
of `aws configure set` calls produces the *same* `~/.aws/config` — it is the
path `refresh_aws_sso.sh` already chose, for the same reason — while letting the
app collect the values in a form it can validate before writing anything.

The interactive path stays available as an escape hatch: onboarding offers a
**Copy command** button that puts the literal `aws configure sso` line on the
clipboard (`Effect::ClipboardSet`, already shipped) for anyone who wants to run
it themselves.

### Validation before writing

The form validates rather than trusting, because a bad value here fails much
later with a confusing error:

- **Account id** — 12 digits.
- **Region / session / profile / role** — non-empty; profile name defaults to
  `<role>-<account>` and must not collide with an existing unrelated profile
  (checked with `aws configure list-profiles`).
- **Start URL** — must parse as https. The org value carries a fragment
  (`…/directory/d-98671f268f#/?tab=accounts`); `sso_start_url` conventionally
  has none. The app **warns and offers** to strip it, and never rewrites it
  silently — the script uses the fragment form and works, so this is a
  suggestion, not a correction.

## The auth state machine

```rust
enum Auth {
    Unknown,                                    // before the first probe
    LoggedOut { reason: String },
    LoggingIn,                                  // a login child is running
    Verifying,                                  // login returned; probing identity
    Active { account: String, arn: String },
    Failed { message: String },                 // stderr, shown verbatim
}
```

The transitions are the script's control flow, made explicit:

`Authenticate` → `LoggingIn` → *(login exits 0)* → `Verifying` → *(identity
probe exits 0)* → `Active`. Any non-zero exit lands in `Failed` with the child's
stderr; a `TimedOut` login lands there with a timeout message.

Two behaviors that the script gets for free and the app must choose:

- **A long, generous login timeout.** `aws sso login` blocks while a human
  authenticates in a browser. Minutes, not seconds.
- **Cancel is real.** `Effect::CancelProcess` kills the child, and
  [[12.3-execution-model|§12.3]]'s zombie rule guarantees the late result is
  dropped rather than arriving after the user gave up.

## Scheduling: probe, never compute

The requirement is re-authentication every six hours against an eight-hour
token. The tempting implementation — set a six-hour deadline, compare elapsed
time — is wrong here, and the reason is worth writing down because it
generalizes to any app fronting an external session.

`<Interval>` and `<Frames>` deliver **session-relative** time
([[12.6-the-process-effect|§12.6]]): `t_ms` since the app started. That clock
does not advance while the machine sleeps and resets when the app restarts. Close
a laptop for ten hours and an app doing deadline arithmetic on `t_ms` concludes
that minutes passed and the session is fresh, while the token expired long ago.
It would be confidently wrong exactly when the user most needs it to be right.

So the app treats AWS as the authority:

1. **`<Interval every={60000} onTick={tick} />`** is the only clock input. Each
   tick updates `now_t_ms` on State; result handlers read that field rather than
   any clock, keeping `reduce` pure ([[05.3-purity-rules|§5.3]]).
2. **A probe on a short cadence** (every few minutes) runs
   `aws sts get-caller-identity --profile <p>`. Exit 0 means the session is
   genuinely usable — it is the same check the user's own tooling would make.
   Non-zero means it is not, whatever any clock believed.
3. **The six-hour deadline is a nudge, not the correctness mechanism.** At
   `now_t_ms - last_login_t_ms >= 6h` the app refreshes. If the deadline never
   arrives because the app restarted, the probe still catches a dead session
   within one probe interval.
4. **A probe also runs at startup**, before anything claims a state.

The invariant: *the app never reports `Active` on the strength of elapsed time
alone.* Every `Active` traces back to a successful identity probe.

### Refresh needs a human, sometimes

An honest constraint the UI must respect. When the SSO session still has a valid
refresh token, `aws sso login` completes without interaction and the six-hour
refresh is genuinely unattended. When it does not, a browser must open and a
person must consent — no scheduler can remove that.

The app therefore treats unattended refresh as a preference, defaulting **on**
(the stated requirement), and stated on screen so a browser tab appearing at
hour six is expected rather than alarming. With it off, the deadline turns the
status into a prominent "needs attention" and waits for the button. A desktop
notification at that moment is the natural companion and waits on
`Effect::Notify` ([[PLAN-NATIVE-INTEGRATIONS]] N3).

The app must also be **running** for any of this. A menubar/tray presence and
launch-at-login are the real fix and belong to [[19-platform-integration|§19]]
and [[20-packaging|§20]]; until then the window stays open, and that is a stated
limitation rather than a hidden one.

## Security

The app's whole reason to exist is handling credentials, so these are
requirements, not preferences:

1. **No secret is ever captured.** The allowlist has no verb that prints one.
   `export-credentials` is excluded for precisely this reason, which is also why
   the exact-expiry countdown is not offered.
2. **No secret, token, or identity in KV.** Account and ARN from a probe live in
   memory for display and are gone on exit. Only non-secret configuration
   persists.
3. **Nothing captured is logged**, per [[12.6-the-process-effect|§12.6]] rule 6.
4. **Login output is displayable, never storable.** A verification URL or device
   code is single-use and short-lived; showing it is fine, persisting it is not.
5. **The app never writes `~/.aws/credentials`** and never implements
   `credential_process`. Credential storage is the CLI's job.
6. **argv only.** Every user-supplied value — profile, URL, role — is one argv
   element ([[12.6-the-process-effect|§12.6]] rule 1). There is no code path
   where a typed value becomes a command.
7. **Snapshots and fixtures use invented identities** ([[27-first-party-applications|§27]]
   rule 4). No committed PNG contains a real account number or ARN.

## Determinism notes

Two traps specific to this app:

- **No local-time formatting in a projection.** `"Verified at 10:42"` renders
  differently per machine timezone, and a projection field is on the paint path,
  so it would break byte-exact snapshots. Durations from the tick domain
  (`"verified 3 minutes ago"`) are deterministic; use those, or UTC.
- **Enum-valued attributes cannot be bound** (deferred in
  [[26-open-questions|§26]]). Status colour comes from `<if>` around literal
  `tone=` values, not `<Badge tone={status_tone}>`.

## UI surface

Steady state, sketched in the shipped grammar — [[06.2-closed-grammar|§6.2]]
constructs and catalog components only:

```lx
<Column gap={12} padding={16}>
  <Interval every={60000} onTick={tick} />

  <Row gap={8} cross="center">
    <Text bold grow>AWS Session</Text>
    <if test={is_active}>
      <Badge tone="success" testId="status">Active</Badge>
      <else><Badge tone="danger" testId="status">Signed out</Badge></else>
    </if>
  </Row>

  <if test={has_error}>
    <Alert tone="danger" title="Login failed" testId="error">{error_message}</Alert>
  </if>

  <Card>
    <Text size="sm" muted testId="identity">{identity_line}</Text>
    <Text size="sm" muted testId="verified">{verified_ago}</Text>
    <Text size="sm" muted testId="next">{next_refresh}</Text>
  </Card>

  <Row gap={8}>
    <if test={is_busy}>
      <Button variant="secondary" onPress={cancel} testId="cancel">Cancel</Button>
      <else>
        <Button variant="primary" onPress={authenticate} testId="authenticate">Authenticate</Button>
      </else>
    </if>
    <Spacer />
    <Button variant="ghost" onPress={toggleConfig} testId="show-config">Show config</Button>
  </Row>

  <if test={show_config}>
    <Card>
      <for each={config_rows} as="c" key={c.key}>
        <Row gap={8}><Text size="sm" muted grow>{c.key}</Text><Text size="sm">{c.value}</Text></Row>
      </for>
      <Row gap={8} cross="center">
        <Switch checked={auto_refresh} onToggle={toggleAutoRefresh} testId="auto-refresh" />
        <Text size="sm" muted>Refresh automatically every 6 hours</Text>
      </Row>
      <Row gap={8}>
        <Button variant="ghost" onPress={copyExportLine} testId="copy-export">Copy AWS_PROFILE line</Button>
        <Spacer />
        <Button variant="ghost" onPress={restartOnboarding} testId="reconfigure">Re-run setup</Button>
      </Row>
    </Card>
  </if>
</Column>
```

`config_rows` is a [[06.3-grammar-restrictions|§6.3]] projection built from
`aws configure get` reads plus the app's own KV values, so "show the current
config" reports what is *actually* on disk rather than what the app believes it
wrote. `copyExportLine` reuses shipped `Effect::ClipboardSet` to hand over
`export AWS_PROFILE=<p>`, the script's `--export` mode.

## Testing

The ladder is unusually valuable here because the real thing is slow,
interactive, and network-bound — and none of that touches the tests
([[15.4-integration-tests|§15.4]]).

| Kind | What it pins |
|---|---|
| **Unit** | Every `Auth` transition; validation (12-digit account, https URL, fragment warning); the deadline/probe arithmetic against hand-fed `Instant`s |
| **Component** | Mode selection (preflight blocks onboarding); button/label state per `Auth`; `has_source("interval")` |
| **Integration** | The full script equivalence: onboarding emits the exact `aws configure set` argv sequence; `authenticate` emits `sso login` then, on exit 0, `get-caller-identity`; non-zero exit surfaces stderr; `TimedOut`; cancel drops the late result; a probe failure after a stale deadline re-triggers login |
| **Snapshot** | Preflight-failing, onboarding-empty, onboarding-invalid, active, signed-out, error, config-shown — fixture identities only |

The integration tests are the real regression guard: they assert the *argv the
app would run*, which is the same assertion as "the app still does what
`refresh_aws_sso.sh` does."
