# 19.2 Keyboard shortcuts: declarations, not handlers

## In this vault

- Parent: [[19-platform-integration]]
- Sibling: [[19.4-desktop-os-matrix|§19.4]]
- Leans on: [[05.2-what-the-macro-generates|§5.2]] (reflected action names), [[10.1-text-entry|§10.1]] (the editing keymap this must not fight), [[15-testing-architecture|§15]] (harness parity)

---

App-level shortcuts are **data validated at startup**, the same shape as
every other Libra declaration — no `onKeyDown` handlers, no code in the
keymap. An app declares chord → action pairs; the runtime rejects the
table at launch if any chord fails to parse or any action name fails to
reflect (load-time validation, same posture as markup handler names).

```rust
fn shortcuts() -> Vec<Shortcut> {
    vec![
        Shortcut::action("cmd+n", "newNote"),
        Shortcut::action("cmd+backspace", "deleteNote"),
        Shortcut::with_arg("cmd+1", "jumpFolder", "1"),
        Shortcut::action("escape", "clearQuery"),
    ]
}

libra::app! { state: Notes, /* … */ shortcuts: Notes::shortcuts }
```

## The pieces

| Piece | Layer | Contract |
|---|---|---|
| `Shortcut { chord, action, arg }` + `Chord`/`parse_chord` | `libra-core` | Pure — no winit types, so the shell and harness share one parser and one table |
| `App::shortcuts()` (static; default empty) | `libra-core` | Shortcuts are fixed per app, like the reference SDK's `app.zon` — state-dependent enablement is the *action's* job (a no-op reduce), not the table's |
| `shortcuts:` field | `app!` (§5.8) | Optional; a path to the fn, mirroring `init:`/`subscriptions:` |
| Chord matching + dispatch | shell (`libra-platform`) | Built once at startup; a table error is a startup panic naming the bad entry |
| `press_shortcut("cmd+n")` | harness (`libra-test`) | Same parser, same table, same precedence — a shortcut test never re-implements the keymap |

## Chord grammar (closed)

Lowercase, `+`-joined: `modifier* + key`. Modifiers: `cmd` (the
platform-primary modifier — Super on macOS, Ctrl elsewhere), `ctrl`,
`alt`, `shift`. Keys: a single character (letters, digits), or the named
set `escape` / `backspace` / `delete` / `enter` / `space` / `tab` /
`up` / `down` / `left` / `right`. Anything else is a parse error with
the offending chord in the message.

**v1 matching is explicit, not implied.** The table above is the *authoring*
meaning of `cmd`. The shell currently treats Super **or** Control as `cmd` on
every OS (`try_shortcut`), so Ctrl+N fires on macOS and Win+N can fire on
Windows. Menu accelerators ([[19.3-native-menus|§19.3]]) still emit Super on
macOS and Control elsewhere. That split is a documented v1 simplification
([[19.4-desktop-os-matrix|§19.4]]); closing it means picking one rule and
applying it to shell, menus, and harness together — do not leave the paths
disagreeing quietly.

## Precedence (the rule that keeps §10.1 intact)

1. **A focused text control owns its keys.** Un-modified keys and the
   editing-reserved chords (`cmd+c/x/v/z/a`, plain arrows/Home/End,
   Textarea's Enter/Up/Down) never reach the shortcut table while an
   Input/Textarea has focus. `escape` while focused blurs (existing
   §10.1 behavior) — it does not dispatch.
2. **Everything else falls through to the table.** `cmd`-modified chords
   that the editor doesn't claim (e.g. `cmd+n`) fire even while typing —
   platform convention.
3. Unfocused, the whole table is live.

## Dispatch and payloads

A `Shortcut` without `arg` resolves via `action_by_name` (unit action);
with `arg` via `action_with_str` (the arg is a **static string** from
the declaration — `"cmd+1" → jumpFolder("1")`). No computed payloads:
if a shortcut needs context (the selected note, say), the action reads
it from State — same rule as markup dispatch (§6.2).

## Determinism

A shortcut is just another route into the action queue — the dispatched
action lands in the log like any click. Nothing here touches the paint
path; harness `press_shortcut` drives the same table, so shortcut flows
are unit-of-the-keymap testable with zero shell involvement.
