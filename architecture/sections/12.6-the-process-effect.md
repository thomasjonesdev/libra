## The shape

```rust
/// A program to run — *data*, not a `std::process::Command`:
/// comparable, serializable, replayable, and assertable in a test.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct CommandSpec {
    /// Program name, resolved against the runtime allowlist. Never a
    /// shell line.
    pub program: String,
    /// argv — one element per argument, already split.
    pub args: Vec<String>,
    /// Additive environment. The runtime supplies a filtered parent env.
    pub env: Vec<(String, String)>,
    pub cwd: Option<PathBuf>,
    /// Part of the *description*: the runtime kills the child when it
    /// elapses and reports `ProcessStatus::TimedOut`.
    pub timeout_ms: Option<u64>,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ProcessResult {
    pub status: ProcessStatus,
    pub stdout: Vec<u8>,
    pub stderr: Vec<u8>,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum ProcessStatus {
    Exited(i32),
    /// Terminated by a signal (unix) — carries the signal number.
    Signalled(i32),
    /// `timeout_ms` elapsed; the child was killed.
    TimedOut,
    /// Never started: not on the allowlist, not on PATH, permission.
    SpawnFailed(String),
}

// In the Effect enum:
Process       { id: Option<ProcessId>, command: CommandSpec,
                on_done: ActionCtor<ProcessResult, M> },
CancelProcess { id: ProcessId },
```

`ProcessId` mirrors `TimerId`, and `CancelProcess` follows [[12.3-execution-model|§12.3]]'s zombie rule: the child is killed, and a result that was already in flight is dropped rather than delivered. `update` never sees a cancelled process complete.

## Normative rules

1. **argv, never a shell.** There is no `sh -c` path and no string that gets split by the runtime. This is the entire security posture of the effect: a profile name, a URL, or a role typed by a user lands as one argv element and therefore *cannot* become a command, a redirect, or a second statement. An API that took a command string would be a defect, not a convenience.
2. **The program is allowlisted.** `CommandSpec::program` is a bare program name checked against a runtime allowlist and resolved through `PATH` at spawn time. A name containing a path separator is rejected with `SpawnFailed`. Apps do not get to run arbitrary binaries because they can construct a `String`.
3. **Environment is filtered, then augmented.** The child gets an allowlisted subset of the parent environment (the variables a CLI genuinely needs — `HOME`/`USERPROFILE`, `PATH`, platform locale) plus the spec's explicit pairs. Nothing is inherited implicitly, so a token that happens to be in the parent env does not silently reach a child.
4. **Worker pool, never the shell, never the main thread.** A subprocess may block for minutes — an interactive browser login is the motivating case ([[27.1-aws-sso-session-manager|§27.1]]). It runs on the [[12.3-execution-model|§12.3]] pool like `Http`, not inline in `Shell::dispatch` the way `SetTheme`/`ClipboardSet` do.
5. **The timeout is in the description.** Not a runtime constant, not a wall-clock read in the app. Because it is data, a test asserts the timeout an app chose without waiting for it.
6. **The runtime never logs captured output.** stdout and stderr of a process effect are not traced at any level. The runtime cannot know which bytes are secret, so it treats all of them as if they were.
7. **Harness parity, per [[PLAN-NATIVE-INTEGRATIONS]] rule 2.** `fx::process()` and `fx::process_program("aws")` match; `resolve_process(effect, ProcessResult { … })` feeds a fixture. No test ever runs a real binary — the fixtures *are* the test surface, exactly as `HttpResult` fixtures are for network flows ([[15.4-integration-tests|§15.4]]).
8. **Captured output is not on the paint path.** It reaches pixels only by way of State that a result action set, so snapshots stay byte-exact on fixtures ([[appendix-a-determinism-checklist|Appendix A]]).

## Wall-clock time, and why this effect forces the question

[[05.3-purity-rules|§5.3]] already says the intended shape: *time arrives inside action payloads (`FrameInfo.now`, `HttpResult.received_at`)*. The implemented payloads do not carry it yet — `FrameInfo` and `Instant` expose `t_ms`, session-relative milliseconds, described in code as "all the time the app is allowed to know."

Session-relative time is enough to debounce a save. It is **not** enough to reason about a credential that expires at an absolute instant, because the session clock does not advance while the machine is asleep and resets when the app restarts. An app that computed "6 hours have passed" from `t_ms` would believe a long-expired session was fresh.

Two consequences, both normative:

- **`ProcessResult` carries a wall-clock stamp** — `finished_at_unix_ms: u64`, set by the runtime when the child exits. This is `HttpResult.received_at` finally made real, and it is what lets an app compare against an absolute expiry without reading a clock in `reduce`. Tests set it by hand, so it stays injected time.
- **Liveness is still probed, never computed.** A stamp tells you when something happened; only the authority can tell you whether a session is still valid. See [[27.1-aws-sso-session-manager|§27.1]] — the rule generalizes to any app fronting an external session.

## Out of scope

- Streaming stdout/stderr (`Effect::Spawn` + `<Stream>` delivery) — planned in [[PLAN-STREAM-DELIVERY]], which reuses `CommandSpec` and every rule above unchanged. Reach for it when the *interesting output arrives before the process exits*; `Process` remains correct for everything that only has a result.
- PTY allocation, and therefore *interactive* CLI prompt flows. A program that requires a TTY to answer questions is not drivable by this effect **or by `Spawn`**; drive its non-interactive equivalent instead ([[27.1-aws-sso-session-manager|§27.1]] does exactly this).
- Long-lived daemons supervised by the app; process groups; shell pipelines.
- `stdin` payloads (add when an app needs one — the shape is an obvious `Option<Vec<u8>>`, deliberately not speculated into v1).
